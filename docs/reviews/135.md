## 3. 발견 사항

- 관점: 계약 정합성 · 정확성(경계 조건, 실패 경로) · 보안(입력 검증, Secret) · 테스트 실효성. 조건부 관점(동시성·트랜잭션, 인가)은 열지 않았다(근거: 공유 상태·권한 판정 변경 없음, `--save`는 단일 파일 쓰기).
- Secret 점검(diff 전체 1회): 새 Secret·토큰·디버깅 출력 없음. 수집 출력은 리뷰 파일 내용(결함 요지)을 옮기지 않고 수만 담는다(`test_collect_links_by_branch_key`의 `assertNotIn("토큰 누출", …)`로 확인).
- 경로 안전성: `REVIEW_FILE_PATH`가 키를 `[A-Za-z0-9][A-Za-z0-9_-]*`로 제한해 `..`·하위 디렉터리·`.`으로 시작하는 이름이 들어오지 않는다. `--save`의 키도 같은 검사를 거친다. 경로 탈출 결함은 찾지 못했다.
- MR 본문 두 줄: `review_lines`·`parse_review_lines` 변경 없음, `--save`/`--detail` 없이 출력 동일. 옛 표(심각도 열 없음)·A/B 표기 하위 호환 확인.

### F1 — 기본 2-브랜치 모델에서 예약 수집기는 develop에 병합된 MR의 리뷰 파일을 읽지 못해 `missing`으로 센다
- 단위 / 관점: U2 / 정확성(실패 경로), 계약 정합성
- 근거: 심각도 제안 **중간**. `bin/harness.py` `ROOT_DEFAULTS`가 `default_branch: main`, `integration_branch: develop`(2-브랜치)이고 기능 MR은 develop을 대상으로 한다(`tests/fixtures/metrics/gitlab.json`도 `target_branch: develop`). `core/ci/gitlab/metrics.yml`은 "대상 브랜치는 기본 브랜치" 스케줄에서 돌고, `committed_review`는 그 checkout(`--checkout` 기본 `.`)에서 파일을 읽는다. develop→main 릴리스 전까지 그 주의 기능 MR은 모두 `missing`이 되고, 리포트 "세지 못한 MR"·주간 요약의 최근 주 값이 비게 된다. 테스트(T11)는 checkout에 파일을 미리 둬 이 상황을 다루지 않고, README는 "예약 파이프라인은 기본 브랜치 checkout 루트에서 돈다"고만 적어 이 제약을 알리지 않는다.
- 영향과 제안: 기본 설치에서 새 지표가 최근 주에 대해 체계적으로 비어 보이고 `missing`(파일 없음)과 "아직 기본 브랜치에 없음"이 구분되지 않는다. MR의 `target_branch` 기준으로 읽거나(예: integration 브랜치 ref에서 `git show <ref>:<path>`, API 호출 없이 가능), 최소한 README·metrics.yml에 "2-브랜치면 스케줄 대상을 integration 브랜치로 두거나 릴리스 뒤에 채워진다"를 적고, 대상 브랜치가 checkout과 다른 경우를 별도 상태로 남기는 방안을 검토한다.

### F2 — 같은 이슈 키의 MR이 둘 이상이면 리뷰 파일이 덮어써지고 두 MR 모두 최신 내용으로 이중 집계된다
- 단위 / 관점: U2·U3 / 정확성(경계 조건), 테스트 실효성
- 근거: 심각도 제안 **중간**. 파일 이름은 이슈 키(`docs/reviews/<키>.md`)이고 연결 조건은 "MR이 그 파일을 바꿨고 소스 브랜치에 같은 키가 있다"(`committed_review`)뿐이다. 기여 규칙은 "한 브랜치에는 이슈 하나"만 정하고 이슈 하나에 MR 하나를 강제하지 않는다(`docs/contributing.md` 10행). 같은 이슈의 후속 MR(`fix/12-…`)이 자기 리뷰를 `--save`하면 `docs/reviews/12.md`를 덮어써 첫 MR의 리뷰는 병합 상태에서 사라지고, 두 MR 모두 연결돼 수집 시점의 같은 파일 내용을 두 번 센다. 이슈 본문은 "MR당 최종 리뷰 파일 하나"이고 README는 "같은 리뷰를 두 번 세지 않는다"고 적었지만 같은 키 경우는 막지 못한다. 이 경우의 테스트가 없다.
- 영향과 제안: 주별 `review_files`의 발견·심각도·발견 세션 합이 부풀고 앞 MR의 기록은 잃는다. (a) 규칙으로 "이슈당 리뷰 파일을 커밋하는 MR은 하나"를 명시하거나, (b) 같은 경로를 연결한 MR이 여럿이면 그 파일을 새로 추가한 MR만 잇는다(GitLab diffs의 `new_file`, GitHub files의 `status: added`로 API 호출 추가 없이 판별), 혹은 `--save`가 기존 파일을 덮어쓸 때 경고한다. 어느 쪽이든 같은 키 MR 두 개 테스트를 더한다.

### F3 — `--save`가 현재 디렉터리를 저장소 루트로 가정해 키트 명령·하위 디렉터리 실행 시 엉뚱한 곳에 조용히 쓴다
- 단위 / 관점: U3 / 정확성(실패 경로)
- 근거: 심각도 제안 **낮음**. `summary.py`와 `bin/harness.py` 모두 `Path.cwd()`를 저장 루트로 넘긴다. 키트의 다른 요약 명령은 `events summary ../my-project`처럼 대상 경로를 받는데, `python bin/harness.py review summary ../my-project/plans/12-review.md --save`는 대상 저장소가 아니라 키트 저장소의 `docs/reviews/12.md`에 쓴다. 대상 저장소에서도 `plans/` 안에서 `python ../.harness/summary.py review 12-review.md --save`로 실행하면 `plans/docs/reviews/12.md`(gitignore 밑)에 써져 커밋되지 않고, 출력은 정상 두 줄이라 알아채기 어렵다. `summary.py`는 이미 `harness_dir.parent`(저장소 루트)를 알고 있다. 도움말·README에 "저장소 루트에서 실행"이라고 적혀 있어 문서상 위반은 아니다.
- 영향과 제안: 리뷰 파일이 커밋되지 않아 지표에서 빠지거나 키트 저장소를 오염시킨다. `summary.py`는 `harness_dir.parent`, 키트 명령은 리뷰 파일이 속한 저장소 루트(예: `plans/`의 부모 또는 `git rev-parse --show-toplevel`)를 쓰거나, 최소한 쓴 경로를 stderr로 한 줄 알린다.

### F4 — README가 약속한 `invalid` 경로(1 MB 초과·UTF-8 아님)에 테스트가 없다
- 단위 / 관점: U2·U6 / 테스트 실효성
- 근거: 심각도 제안 **낮음**. README "커밋된 최종 리뷰 파일"은 "1 MB를 넘거나 UTF-8이 아니거나 7장 표가 틀리면 `invalid`"라고 적었고 `committed_review`에 `REVIEW_FILE_MAX_BYTES`·`UnicodeDecodeError` 분기가 있지만, `test_unlinked_missing_invalid`는 표 오류(심각도 `치명`)만 `invalid`로 확인한다. 크기·디코딩 분기는 실행되지 않는다.
- 영향과 제안: 분기가 깨져도(예: 예외 종류 변경) 수집기 전체가 예외로 종료될 수 있는데 잡히지 않는다. 1 MB 초과 파일과 잘못된 UTF-8 바이트 파일 두 사례를 T12에 더한다.

### F5 — 발견 세션 `single`의 실제 기준이 문서("발견 번호만 있으면")보다 넓다
- 단위 / 관점: U1·U5 / 계약 정합성
- 근거: 심각도 제안 **참고**. README는 "세션 표기 없이 발견 번호만 있으면 단일 세션(W1)"이라 적었지만 코드는 `single = _found(cell)`로 빈 칸·대시·"해소…"가 아닌 모든 텍스트를 단일 세션으로 센다. 예를 들어 엄격 대조표에서 번호 없이 `R1, R2`로 적으면 `FIRST_SESSION`·`SECOND_SESSION`이 모두 불일치해(번호 필수) 독립 중복이 아니라 `single`로 들어간다(직접 확인).
- 영향과 제안: 표기 실수가 오류 없이 다른 분류로 들어간다. 문서를 실제 기준("세션 표기가 없으면 단일 세션")으로 고치거나, 엄격 표기 오류를 잡고 싶다면 숫자 없는 `R1`/`R2`/`A`/`B` 낱말을 경고한다.

## 7. 처리 (작성자가 반영 뒤 채운다)

리뷰 세션이 아니라 작성자가 발견 사항마다 처리를 적는다. 엄격(W2)이면 두 세션의 같은 결함을 한 행으로 묶는다.
`python .harness/summary.py review <이 파일> --save`가 이 표를 세어 PR 본문 `## 리뷰 결과`에 붙일 두 줄을 만들고(지표 8),
이 파일을 최종 리뷰 `docs/reviews/<이슈 번호>.md`로 저장한다. 그 파일을 PR과 함께 커밋하며, 커밋 전에 Secret·개인정보가 없는지 확인한다.
`결함`에는 한 줄 요지를, `심각도`는 높음·중간·낮음·참고 중 하나를 적는다. `발견`에는 리뷰 세션과 번호(W1이면 `F1`,
W2면 `A F1, B F3` 또는 `R1 F1, R2 F3`)를, `처리`는 채택·기각·후속·판단 필요 중 하나로 시작한다.

플랜 승인: 해당 없음(표준). 커밋 여부는 사용자 결정 2026-10-20 B안.
