# AGENTS.md

이 문서는 이 저장소에서 작업하는 AI 코딩 도구가 따라야 할 기본 규칙이다.
도구가 이 파일을 자동으로 읽지 않는 경우 사용자가 작업 시작 전에 내용을 전달한다.

이 문서는 AI가 하나의 작업을 시작·수행·검증·보고하는 절차를 정의한다. 여러 작업자와
AI가 같은 저장소에서 동시에 작업할 때의 작업 공간 분리, 충돌 위험 분류, 합의가 필요한
변경과 문서 종류별 우선순위는 아래 관련 문서를 따른다.

{{related_docs}}

## 1. 기준과 문서 확인

요구사항과 문서가 충돌하면 다음 순서로 판단한다.

1. 현재 작업에 대해 사용자가 명시적으로 확정한 지시
2. 현재 {{issue_noun}}의 확정 요구사항과 팀 합의
3. 저장소에 적용된 API, DB Schema 및 공통 계약
4. `AGENTS.md`와 저장소의 협업·개발 문서
5. 외부 기획·설계 문서

상위 기준도 기존 계약 변경을 자동으로 허가하지 않는다. 기준이 불일치하거나 확정
여부가 불분명하면 임의로 구현하거나 기존 코드를 되돌리지 않고 확인한다.

기존 {{issue_noun}}을 수행하는 경우 해당 항목과 변경 대상 디렉터리의 `README.md`를
먼저 확인하고, 변경 경로에 해당하는 영역의 `AGENTS.md`가 있으면 함께 적용한다.

## 2. 작업 시작

- 기존 {{issue_noun}}을 수행하는 경우 연결된 {{issue_key}}와 작업 목적을 확인한다.
  본문에 고정 양식을 요구하지 않으며, 항목 내용과 저장소 상태를 바탕으로 작업 범위를
  해석한다.
- 시작 전에 다음을 확인한다. 담당자·진행 상태와 관련 열린 {{pr_noun}}, 현재 브랜치와
  기준 브랜치, 커밋되지 않은 변경과 새 파일, 원격 `{{integration_branch}}`과의 차이, 같은
  파일을 수정 중인 다른 업무, 공통 계약이나 설정 변경 여부.
- {{tracker_name}} 또는 {{platform}} 상태를 직접 확인할 수 없으면 확인하지 않은 내용을
  추측하지 않고 사용자에게 알린다.
- 기존의 커밋되지 않은 변경은 사용자의 작업으로 간주하고 보존한다.
- 기존 {{issue_noun}}을 수행하는 경우 최신 `{{integration_branch}}`에서 {{issue_key}}가
  포함된 작업 브랜치를 사용한다.
- 기존 작업을 재개하거나 인계받으면 브랜치, 변경 파일, 최근 커밋과 검증 상태를
  저장소에서 다시 확인한다.
- 별도 지정이 없으면 구현과 검증까지 수행한다. 커밋과 {{pr_noun}} 생성은 명시적으로
  요청받은 경우에만 수행한다. {{pr_noun}} 생성을 요청한 경우 필요한 Push까지 수행할 수
  있다. 병합은 사람이 한다.
- 수정 전에 작업 목적({{issue_key}}), 변경 범위, 검증 계획, 공통 파일 변경과 충돌
  위험, 확인이 필요한 사항을 간결하게 알린다. 해당 없는 항목은 적지 않는다.
  설명이 부족하지만 안전하게 추론할 수 있으면 가정을 명시하고, 결과를 크게 바꾸는
  선택은 질문하고 답을 받은 뒤 진행한다.

## 3. 변경 범위

- 하나의 브랜치에는 하나의 {{issue_noun}}만 포함한다.
- {{issue_noun}}의 목적을 벗어나는 변경을 임의로 추가하지 않는다.
- 범위 밖의 문제를 발견하면 현재 작업에 섞지 않고 후속 {{issue_noun}}을 제안한다.
- 사용자 요청과 무관한 포맷팅, 파일 이동, 이름 변경, 의존성 갱신을 하지 않는다.
- API 계약, DB Schema, 공통 타입, 환경 변수, 인프라와 보안 정책은 임의로 결정하지 않는다.
- 새 의존성이나 서비스 경계를 추가·변경하기 전에 사용자와 합의한다.

## 4. 기존 작업 보호

- 다른 사용자나 AI의 변경을 삭제, 되돌리기 또는 덮어쓰지 않는다.
- `git reset --hard`, 강제 checkout, 무단 stash 삭제처럼 복구하기 어려운 명령을 사용하지 않는다.
- 작업 브랜치를 전환하기 전에 커밋되지 않은 변경의 소유자와 목적을 확인한다.
- 동일한 로컬 저장소에서 여러 업무를 동시에 처리할 때는 업무별 브랜치와 별도
  Git worktree를 사용한다.
- 동일한 worktree에서 여러 AI가 동시에 파일을 수정하지 않는다.
- 동일 {{issue_noun}}은 명시적으로 협업하기로 한 경우를 제외하고 여러 작업자나 AI가
  동시에 구현하지 않는다.

## 5. 충돌 예방

다음과 같은 공통 변경은 구현 전에 영향 범위를 알리고 관련 작업과의 중복을 확인한다.

- 공통 설정 및 빌드 파일
- 의존성 및 lock 파일
- CI/CD와 배포 설정
- 환경 변수 예시 및 비밀 관리 방식
- DB migration 및 schema
- 공통 API 계약, DTO와 타입
- 공용 컴포넌트와 공유 모듈

API 계약 또는 DB Schema 변경은 영향받는 담당자 간 먼저 합의한다. 여러 작업자가 동시에
의존하는 공통 계약은 선행 작업으로 분리하고, 한 기능 안에서 함께 변경해야 하는 계약은
동일 업무 항목에서 범위와 적용 순서를 명시해 처리할 수 있다. AI는 기존 계약을 임의로
깨지 않는다.

## 6. 검증

- 완료 보고 전 요구사항과 변경 범위를 다시 확인한다.
- 변경한 영역의 테스트, 빌드, 정적 검사 또는 가능한 수동 검증을 수행한다.
- diff와 새 파일을 확인하고 불필요한 파일, 디버깅 코드와 Secret이 없는지 검사한다.
- 최신 `origin/{{integration_branch}}`과의 충돌 여부를 확인한다.
- 실행하지 못한 검증과 남은 위험을 명확히 보고한다.
- 실패한 테스트를 숨기거나 테스트를 통과시키기 위해 검증 범위를 임의로 약화하지 않는다.
- 최종 승인과 병합 여부는 사람이 판단한다.

## 7. 커밋과 {{pr_noun}}

- 브랜치, 커밋 및 {{pr_noun}} 규칙은 관련 문서의 Git 규칙을 따른다.
- {{pr_noun}}을 만드는 쪽(AI 포함)은 만들 때 작업한 worktree에서 다음을 실행해 출력으로 본문 절을 채운다. 키트 없이
  저장소 안에서 실행한다. 기록은 작업한 PC에만 있으므로 다른 PC에서 만들지 않는다.
  - `python .harness/summary.py events` → `## hooks 기록`
  - `python .harness/summary.py agent` → `## 에이전트 기록`
  - 리뷰 파일 7장(처리)을 채웠으면 `python .harness/summary.py review <리뷰 파일>` → `## 리뷰 결과`의 두 줄
- 진행 중인 응답의 기록은 응답이 끝나야 남으므로 출력에 빠진다. 커밋을 더 push할 때마다 다시 실행해 본문을
  고친다(예: `gh pr edit --body-file`, `glab mr update`). 병합하는 사람은 절이 오래됐으면 작성자에게 작업한 PC에서
  다시 만들어 달라고 요청한다.

## 8. 완료 보고

작업이 끝났을 때와 {{pr_noun}} 생성 전에 다음 내용을 보고한다. 해당 없는 항목은 적지 않는다.

- 변경한 파일과 핵심 결과
- 수행한 테스트 및 검증 결과
- 수행하지 못한 검증과 남은 위험
- 공통 파일 변경과 충돌 가능성
- 커밋, 브랜치 및 {{pr_noun}} 정보
- 필요한 후속 작업 또는 별도 {{issue_noun}}

## 9. 업무 항목 자동화

- {{issue_noun}} 생성·수정은 사용자가 명시적으로 요청한 경우에만 수행한다.
- 우선순위, 담당자와 상위 항목(Epic 등)은 사용자의 명시적인 지시나 확정된 계획 없이
  변경하지 않는다.
